# Product readiness and evidence boundaries

Review date: 2026-09-06. Status: **REWORK_REQUIRED_NOT_DELIVERED**.
This is the acceptance baseline for the current source candidate, not a release
certificate. Published previews, locally installed versions and an uncommitted
candidate are different artifacts; their test results are not interchangeable.

## Customer outcome and acceptance

MC-GPT has one governed Coder runtime. Native minimum-change decisions remain
authoritative. Benchmark arms are experiments, not six products or six engines.
The intended customer receives an inspectable change and its evidence, or an
actionable blocked result, without having to infer success from agent prose.

| Journey | Required acceptance | Evidence or remaining gap |
| --- | --- | --- |
| Install | Wheel and source distribution contain the same runtime and public skills; clean imports originate from the installed target | Distribution tests; every changed candidate needs its own outside-checkout run |
| Plan a fixture | Exact documented command preserves all nine criteria; no provider execution or task mutation | `tests/test_product_entrypoints.py`; CLI telemetry is disclosed |
| Authorize work | Task, work unit, lease, risk, scope and acceptance identify one current request | `tasks.py`, `task_validation.py`; protected deployment authority remains external |
| Test a change | Nonempty host-selected checks run against a stable post-change source and immutable output paths | `test_execution_evidence.py`, `multicoder.py`; command success is not measured coverage |
| Review and submit | Same-run tests/reviews, exact task revision and source; later failures and concurrent cancellation cannot be overwritten | `tests/test_public_completion.py`; synthetic provider fixtures are not live provider qualification |
| Verify an installation | Detect changed, missing and unlisted runtime source/data, not only wrappers | `tests/test_runtime_integrity.py`; RECORD/local wheel evidence is not a protected trust anchor |
| Operate safely | Secret-free diagnostics, bounded logs, supported cancellation/recovery and clear ownership | Source regressions exist; actual target sandbox, incident drills and service commitments remain required |

| Buy and deploy | Written commercial terms, declared support scope, deployment qualification and required independent approval | Pending; Community Noncommercial terms do not authorize company operational use |

Passing every frozen criterion is necessary for delivery. A skipped mandatory
test, unknown external approval or unresolved in-scope finding prevents a ready
claim. No finite test suite proves zero latent defects or guaranteed market value.

## Real-world evidence distinctions

Loading a skill, printing its banner, finding a provider executable, planning a
mesh run and receiving a provider contribution prove different things. Record
the installed package digest, session identity, requested/served model, route,
run and assignment/envelope identity, outcome and output hashes. Missing usage
telemetry stays unknown; native subagents are not fabricated external providers.

The installed-runtime verifier covers package source/data and identifies excluded
generated bytecode. It does not authenticate the interpreter, dependencies,
arbitrary startup hooks or execution against an independently signed release.
Untrusted workers require a managed sandbox with separate credentials and ledger
authority. Processes sharing a Unix identity are not cryptographically independent.

Completion receipts in the standalone store bind local evidence. Customer release
approval additionally requires the ordered independent challenge, adversarial
verification, re-attestation and final-judge receipts on the final artifact digests.
Local consensus is not a substitute for those authenticated approvals.

## Remaining release blockers

- Clean, reviewed integration on the exact remote head, hosted checks and protected
  provenance/approval for the changed artifact; a green base commit is insufficient.
- Customer target/OS qualification, live provider receipts and managed worker
  isolation. Windows-only checks cannot be waived by a Linux pass.
- Natural-language policy options rejected as unsupported must be implemented and
  tested before advertising them as effective controls. Default execution budgets
  and per-criterion reporting require explicit customer-journey qualification.
  `tasks run` rejects non-default provider/quorum overrides; use the explicit
  `tasks solve-all` or `multi-coder run` contracts when selecting those controls.
- Current-tree, history, tag and release-asset public-boundary inventories must be
  current and complete. History mutation needs a separate approved decision.
- Commercial terms, support capacity, recovery commitments, regulatory
  applicability and substantiated buyer validation. See [investor brief](investor-brief.md).

Source corrections and evidence preparation may continue without merge, release,
production deployment or invented authenticated receipts.
