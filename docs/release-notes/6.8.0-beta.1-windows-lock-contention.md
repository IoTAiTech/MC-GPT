# Windows lock contention hardening

## Scope

MC-GPT serializes append-only compliance and evidence-chain writes with an exclusive lock file. On Windows, an existing lock held by another process or thread can surface as `PermissionError` rather than `FileExistsError`.

## Correction

The lock helper now distinguishes two cases:

1. an existing lock path that is temporarily inaccessible because another Windows handle owns it — treated as normal contention and retried within the bounded timeout;
2. a genuine access denial when no lock path exists — preserved as a fail-closed `PermissionError`.

A stale lock is removed only when its metadata is readable and unlinking is permitted. A still-open Windows lock is never force-deleted merely because its timestamp is old.

## Regression evidence

The durable regression contract covers:

- simulated Windows sharing-violation semantics for an existing lock;
- genuine directory/access denial that must not be masked;
- the concurrent Article 50 disclosure hash-chain test that exposed the platform difference;
- the complete repository test matrix on Linux, macOS and Windows through hosted CI.
